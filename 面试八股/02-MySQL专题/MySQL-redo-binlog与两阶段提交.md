# MySQL：redo、binlog、undo 与两阶段提交

> 范围：MySQL 8.0 / 8.4、InnoDB、开启 binlog 的普通事务。下面是帮助理解的提交模型，不是逐行源码时序；组提交会合并刷盘。示例仅用于学习，未在生产执行。

## 1. 概念：三种日志解决三件不同的事

| 日志 | 所在层 | 主要记录 | 解决什么 | 保存方式 |
|---|---|---|---|---|
| redo log | InnoDB | 页修改的重做信息，常简称物理日志 | 崩溃后重做尚未写入数据文件的修改 | 有容量边界，随 checkpoint 推进复用空间 |
| undo log | InnoDB | 构造旧版本、撤销修改所需的信息 | 事务回滚、MVCC 历史版本读取 | 受事务与 Read View 生命周期影响，由 purge 清理 |
| binlog | MySQL Server | 数据变更事件；ROW 格式记录行变化，不是磁盘页 | 主从复制、配合全量备份做时间点恢复 | 追加到日志文件，轮换并按保留策略清理 |

**不能互相顶替**：binlog 不负责 InnoDB 本地页级崩溃恢复；redo 也不是长期保存的业务流水，不能只拿 redo 当备份。

## 2. 为什么提交了，数据页却不必立即落盘？

假设 `UPDATE account SET balance=balance-10 WHERE id=1`：

1. InnoDB 找到页；不在 Buffer Pool 就读入。修改需要相应锁，并保留撤销所需的 undo。
2. 内存页被修改成**脏页**，同时产生 redo。脏页只是“内存比数据文件新”，并不等于事务已提交。
3. 数据页可能稍后由后台刷盘；在脏页刷入数据文件前，相关 redo 必须先达到持久化要求，这就是 WAL（Write-Ahead Logging）。
4. 崩溃时，通过已持久化的 redo 恢复页，再结合事务状态和 undo 处理未完成事务。

顺序写日志通常比每次提交都随机刷一批数据页便宜。**WAL 强调日志先于相关数据页持久化，不是说 redo 永远只在 COMMIT 时才写。**未提交事务的 redo、甚至包含未提交修改的数据页，都可能先落盘。

## 3. 两阶段提交：为什么需要 prepare？

同一笔扣款既影响本机 InnoDB，也要进入 binlog。如果两个结果各自提交：

- 引擎提交了，binlog 没留下：主库有扣款，从库或恢复出来的库没有。
- binlog 留下了，引擎回滚了：从库有扣款，主库没有。

因此 Server 和 InnoDB 需要统一“这笔事务最终算不算提交”。常见面试模型：

```text
事务执行：修改内存页、产生 undo/redo、准备 binlog 事务事件
       ↓
InnoDB prepare：记录可恢复的“已准备”状态
       ↓
Server 写入完整 binlog 事务，按策略同步
       ↓
InnoDB commit：完成引擎提交
       ↓
客户端收到成功（数据页可以以后刷盘）
```

这里的“两个阶段”是引擎的 prepare 与 commit；binlog 处在协调流程中。内部提交协议不要和应用跨服务的 XA / TCC / Saga 混成一回事。

## 4. 宕机后如何判定？

在日志完整、满足持久化配置且存储正确执行同步的前提下，恢复会关联事务标识（XID）与完整 binlog 事务：

| 宕机时可恢复状态 | 判断方向 |
|---|---|
| 引擎事务尚未 prepare，未形成可提交决策 | 未提交事务应回滚 |
| redo 中是 prepare，但 binlog 无对应完整事务 | 回滚 |
| redo 中是 prepare，binlog 有对应完整事务 | 补做引擎提交 |
| 引擎已完成提交 | 恢复到已提交状态 |

这张表解释了：**没有最后那条引擎 commit 记录，不必然回滚**，还要看协调方留下的提交依据。不是“扫描到一段 binlog 字节就提交”，必须验证完整事务和对应标识。

客户端还可能遇到“提交已成功，成功响应却在网络中丢失”。此时应用看到超时，但数据库已经有数据；重试要靠业务幂等键、唯一约束或查询结果确认，不能盲扣第二次。

## 5. 刷盘参数怎么答？

| 参数 | 常见值 | 含义与风险 |
|---|---|---|
| `innodb_flush_log_at_trx_commit` | 1 | 每次提交要求 redo 写入并同步到持久存储；组提交可共享同步成本 |
| 同上 | 2 | 每次提交写到操作系统缓存，通常定期同步；操作系统/断电故障可能丢近期事务 |
| 同上 | 0 | 通常定期写日志并同步，mysqld 进程故障也可能丢近期事务 |
| `sync_binlog` | 1 | 每个 binlog 提交组要求同步；常与 redo 的 1 配合考虑 |
| 同上 | 0 或较大数值 | 减少同步次数，但扩大故障时的丢日志风险 |

“最多丢一秒”只是默认周期下的常见近似：调度、`innodb_flush_log_at_timeout`、存储行为都会影响窗口。双 1 也不能替代可靠硬件、备份与异地容灾；更不能保证异步从库已经应用完成。

## 6. binlog 格式与组提交追问

- **STATEMENT** 记语句，日志可能小，但非确定函数、上下文差异会增加复制风险。
- **ROW** 记行变化，通常更利于复制确定性；大量行更新可能生成大量日志。DDL 并不是一律变成逐行事件。
- **MIXED** 在两种模式间选择。具体支持与推荐配置按版本核对，不把老参数当永恒规则。
- **组提交**把多笔事务的日志写入/同步组织成批次，减少每笔各做一次同步的开销；不代表把多笔业务事务合并成同一事务。

## 7. 面试口述版

> redo 负责 InnoDB 崩溃恢复，undo 负责回滚和旧版本，binlog 负责复制及备份后的增量恢复。更新先改 Buffer Pool 并记日志，数据页可以异步刷盘。开启 binlog 时，通过 prepare、写 binlog、引擎 commit 协调两边结果；崩溃后用完整 binlog 事务决定 prepared 事务提交还是回滚。持久性还要看刷盘配置，客户端超时也不代表没提交。

## 8. 易错点与检查清单

- 不说“redo 记录原 SQL”“binlog 可以代替 redo”“undo 提交即删”。
- 不把“写入 OS 缓存”和“同步到持久存储”视为同一件事。
- redo 空间紧张时可能被迫推进刷脏页，体现为写延迟上升；不是无限追加。
- 只读核对：`SELECT @@version, @@log_bin, @@sync_binlog, @@innodb_flush_log_at_trx_commit;`。日志名、容量参数因版本变化，先查对应手册再调整。
- 故障恢复练习应在一次性测试库完成；保留备份和日志，不能手删 redo/binlog 试运气。
