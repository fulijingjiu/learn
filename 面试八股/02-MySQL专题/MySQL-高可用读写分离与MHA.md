# MySQL：复制、高可用、读写分离与 MHA

> 范围：MySQL 8.0 / 8.4 复制概念。MHA、MyCat 在旧面试资料中常出现，本篇解释其职责，不把它们默认推荐给所有新项目；具体兼容性、维护状况需选型时核验。

## 1. 概念：这几个目标不一样

| 目标 | 主要解决 | 不能自动解决 |
|---|---|---|
| 主从复制 | 把变更送到另一台实例 | 自动切流、绝对零丢失 |
| 读写分离 | 将可容忍延迟的读取分摊到副本 | 扩大单主写能力、消除复制延迟 |
| 高可用 HA | 节点故障后恢复服务 | 误删恢复、跨地域容灾全部问题 |
| 备份 / PITR | 恢复某个历史时间点 | 持续对外服务 |
| 分库分表 | 分散存储/写入/容量 | 自动解决跨片 JOIN 和事务 |

先明确 RPO（可接受丢多少数据）和 RTO（多久恢复服务），再选方案。复制会把误删也复制过去，所以“有从库就不做备份”是错的。

## 2. 复制链路：收到不等于应用

```text
应用写 → 主库提交并写 binlog
                    ↓ 网络
            副本 receiver / IO 线程
                    ↓
                 relay log
                    ↓
             applier / SQL workers
                    ↓
              副本本地数据
```

旧教材说“一个 SQL 线程重放”，现代版本还支持并行应用，实际并行度受事务依赖、配置与硬件影响。ROW 事件也不是全部还原成原 SQL 再执行。

| 模式 | 提交确认大致等到哪里 | 权衡 |
|---|---|---|
| 异步 | 不等副本确认即可返回 | 主库故障切到落后副本可能丢已确认写入 |
| 半同步 | 等规定数量副本确认接收、写入 relay log 并刷盘；等待点按配置 | 不代表查询副本已可见；超时还可能回退异步 |
| Group Replication 等组复制方案 | 基于组通信/认证协议协调 | 不是把旧异步复制加一个脚本；需理解多数派、网络与一致性设置 |

半同步的等待点和故障语义需要核对参数，不能简化成“从库执行完才提交，所以强一致”。GTID 为事务提供全局身份，便于定位已执行集合与切换，但 GTID 不是数据一致性的魔法开关。

## 3. 读写分离怎么落地？

```text
应用 → 路由层 / 数据源
        ├─ 写、事务内关键读、写后立刻读 → 主库
        └─ 允许延迟的报表/列表读取 → 健康副本池
```

| 方式 | 常见形态 | 注意 |
|---|---|---|
| 应用路由 | 两套数据源、路由注解/策略 | 事务边界和连接绑定必须明确，避免每条语句漂移 |
| 代理 | ProxySQL、MySQL Router 的适用架构等 | 代理自身高可用、连接排空、故障探测也要设计 |
| 分片/治理中间件 | ShardingSphere、MyCat 等 | 不只是“所有 SELECT 发从库”；SQL、事务和分片限制更复杂 |

不是所有代理都具备同样的 SQL 解析或自动读写分离能力。比如 Router 常承担特定集群拓扑的路由职责，不能仅凭名字推断所有部署都会自动拆分读写。

### 写后读为什么读不到？

主库写成功后马上从副本查询，可能落在“收到但未应用”或“尚未收到”的窗口。常见策略：

1. **强一致路径直接读主库**，最容易解释和验证。
2. 对用户或请求短期粘主；注意“固定等 500ms”只是经验，不保证任何负载下同步完成。
3. 需要精细控制时，基于事务 GTID 水位等待副本应用，设置超时并回退主库；不是只看延迟指标为 0。
4. 普通列表可明确接受最终一致，UI 给出刷新语义。

## 4. MHA 到底做什么？

MHA（Master High Availability）是传统 MySQL 主从架构中的故障管理工具，常见组成是 Manager 与节点侧工具。它协调故障发现、补齐日志、提升新主和重挂其他副本，并通过脚本等配合切换访问入口。

典型切换心智流程：

1. 多角度确认主库不可服务，避免只有监控节点网络断了就误判。
2. **隔离旧主（fencing）**，阻止它恢复后继续接写，避免双主分叉。
3. 尽可能收集旧主尚未传播的 binlog，比较候选副本进度并补齐差异。
4. 提升合适副本，其他副本改跟新主，路由/VIP/连接池切流。
5. 校验业务与复制；旧主恢复后先作为受控节点重建/追平，不直接抢回写入口。

**MHA 不保证任何故障下都零丢数据**：旧主硬盘坏、网络不可达时，可能无法抢救最后日志。半同步能降低某些风险，但不能抹去回退异步、选主错误和故障模型限制。MHA 本身也不是常驻 SQL 转发代理。

## 5. 排障检查清单（只读取证）

```sql
SHOW REPLICA STATUS;
SELECT @@read_only, @@super_read_only;
SELECT @@global.gtid_executed;
```

旧版本可能使用 `SHOW SLAVE STATUS` 与旧字段名；按实例版本核对。`\G` 是 mysql 客户端竖排显示方式，不是 JDBC 通用 SQL 语法。

| 检查 | 想回答的问题 |
|---|---|
| IO/receiver 与 SQL/applier 是否运行 | 没收到还是没应用？是否有明确错误？ |
| Last IO / SQL error 与 worker 状态 | 网络、权限、缺日志、冲突还是应用 SQL 慢？ |
| GTID 已接收/已执行集合、业务采样 | 落后多少事务？是否真的达到需要的水位？ |
| 延迟与吞吐的趋势 | 偶发大事务、DDL、读负载抢资源、磁盘或网络瓶颈？ |
| 路由和实际连接目标 | 请求是不是还连旧主？连接池是否需要重建？ |
| 旧主隔离与只读状态 | 是否存在两个可写入口？普通只读配置能否被高权限绕过？ |

`Seconds_Behind_Source=0` 不是“每个事务都已实时同步”的证明；指标可能受接收状态、采样与并行应用影响。不要靠跳过复制错误、关闭持久化、直接改副本数据来掩盖问题。切换、改只读、重建复制和终止连接是变更操作，必须先审批与演练。

## 6. 面试口述版

> 复制把 binlog 传到副本再应用，读写分离用副本分摊可容忍延迟的读，高可用负责故障后选主和切流，这三个不是一回事。异步可能丢最后一段写，半同步通常只保证收到日志，不等于从库读已可见。MHA 是传统故障切换管理工具，会尽量补日志并提升副本，但不能承诺所有故障都零丢失。我还会设计旧主隔离、连接切换、写后读主库和备份恢复演练。

## 7. 易错点与最小演练目标

- 一主多从不能直接提高主库写吞吐；更多副本还会增加复制维护成本。
- 不把“主库磁盘刷了双 1”与“任何新主都含该事务”划等号。
- 演练记录：故障前写入序号、客户端确认结果、选主用时、切流用时、恢复后数据校验、旧主归队步骤。区分实测 RPO/RTO 与目标，不编造压测数据。
