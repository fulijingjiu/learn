# MySQL：深分页与分布式主键选型

> 范围：MySQL 8.0 / 8.4、InnoDB。两个主题的共同点是“按什么稳定顺序定位数据”。以下 SQL 针对示意表，需结合真实数据验证计划。

## 1. 概念：深分页是什么，为什么慢？

```sql
SELECT id, created_at, amount
FROM orders
WHERE status = 'PAID'
ORDER BY created_at DESC, id DESC
LIMIT 1000000, 20;
```

`OFFSET=1000000` 不是跳到 B+ 树“第 100 万行”的直接地址。通常要沿访问路径找出前 1000020 条符合要求的候选，丢弃前面部分，再返回 20 条；没合适排序索引时还可能额外过滤与排序。

若按二级索引扫描但要大量回表取 `amount`，浪费更大。**有 ORDER BY / 有索引不等于深分页已解决**，只是可能省掉额外排序。

## 2. 三种方案怎么选？

| 方案 | 优点 | 限制 | 适合 |
|---|---|---|---|
| OFFSET + 合适索引 | 页码直观，能跳页 | 越深越需扫描；并发插删导致页漂移 | 小页数后台 |
| 延迟关联 | 先覆盖索引找少量 ID，再取整行 | 仍需扫描 offset 那段索引，不是 O(1) | 必须保留深页码 |
| Keyset / 游标分页 | 从上一页最后一个排序键接着找 | 不能天然跳任意页；需稳定排序键 | 时间线、滚动列表、批处理 |

先建与等值筛选和排序匹配的候选索引，比如 `(status, created_at, id)`，再测是否真正选用。`created_at` 相同很常见，用唯一的 `id` 兜底保证确定顺序。

### A. 延迟关联：只为最后一页取整行

```sql
SELECT o.id, o.created_at, o.amount
FROM orders AS o
JOIN (
    SELECT id, created_at
    FROM orders
    WHERE status = 'PAID'
    ORDER BY created_at DESC, id DESC
    LIMIT 1000000, 20
) AS page ON page.id = o.id
ORDER BY page.created_at DESC, page.id DESC;
```

内层尽量用覆盖索引，外层为 20 个 ID 取明细。必须在外层也写 `ORDER BY`，子查询排序不会自动保证最终 JOIN 输出顺序。收益取决于索引宽度、回表代价和缓存；不要承诺固定倍数。

### B. Keyset：保存的是排序锚点，不是页码换算

上一页最后一条是 `(last_created_at, last_id)`，下一页：

```sql
SELECT id, created_at, amount
FROM orders
WHERE status = 'PAID'
  AND (
      created_at < :last_created_at
      OR (created_at = :last_created_at AND id < :last_id)
  )
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

`:参数名` 是说明用的绑定占位符，实际按驱动替换，不要拼接用户文本。也可比较行构造器 `(created_at,id)`，但优化器对不同写法的利用能力与版本有关，先验证计划。

**不要求 id 连续**：删除留下的空洞不影响 `id > last_id` 一类锚点查询。错误做法是用“页码×页大小”计算一个 id 当偏移；那是假设连续且无额外筛选。

## 3. 并发下的正确性与导出

- 排序字段最好不可变、非空；允许改 `created_at` 会让记录跨页移动，游标也不能自动保证整段读取是同一快照。
- 游标需绑定筛选条件、排序方向、租户；必要时做签名或服务端保存，防止被篡改越权。
- 实时信息流可以接受新增数据出现在刷新后；财务导出若要求一致时点，要明确快照/截止边界或用专门导出流程，别长期占着线上事务翻百万页。
- 批处理常以单调 id 做水位分批，但自增 ID 的分配顺序不等于提交顺序；并发事务晚提交可能被水位越过。严格不漏应结合一致性快照、CDC/提交水位或重叠扫描加幂等去重设计。
- 不一定每次都算昂贵的精确 `COUNT(*)`；可用 `LIMIT page_size+1` 判断是否有下一页。

## 4. 为什么还要分布式主键？

单库自增很省事；多库独立自增可能碰撞，业务还可能要求先生成订单号再写库。选型要看唯一性、顺序性、长度、吞吐、部署依赖、时钟风险和可预测性。

| 方案 | 顺序/长度 | 优点 | 主要代价 |
|---|---|---|---|
| 单库 BIGINT 自增 | 本库大致递增，8 字节 | 简单、索引紧凑 | 非全局方案；不连续，不代表提交顺序 |
| 号段（集中分配区间、本地发号） | 区间内递增，常用 64 位 | 单次分配后可本地高吞吐 | 号段存储高可用、预取、崩溃留洞 |
| 随机 UUID（如 v4） | 128 位、随机 | 无中心，碰撞概率极低 | 大且随机，索引局部性差；不是数学上绝无碰撞 |
| 时间有序 UUID（如 v7） | 128 位、时间大致有序 | 局部性优于完全随机 UUID | 仍较宽；同毫秒不必全局严格递增 |
| Snowflake 类 | 常用 64 位，时间+节点+序列 | 本地生成，大致趋势递增 | 时钟回拨、节点号重复、序列溢出 |
| Redis INCR / 发号服务 | 常用整型 | 实现直观 | 网络依赖、持久化与故障切换需防重复 |

“分布式后只能 UUID”不对，号段与 Snowflake 都常见。也可以内部用紧凑主键、外部用不可枚举业务标识，但需额外唯一约束与映射。

## 5. 主键为什么会影响整张表？

InnoDB 聚簇索引按主键组织记录；二级索引叶子也保存主键值。主键越宽，多个二级索引会一起变胖，缓存利用率下降。随机主键还可能增加离散页写与页分裂；递增主键通常局部性更好，但高并发也可能有末端热点，不能说永远最优。

Snowflake 不是全局严格递增，也不是保密令牌。必须设计节点号分配、时钟回拨处理、重启状态保护与唯一约束；用 64 位 ID 给 JS 前端时注意超过 `Number.MAX_SAFE_INTEGER`，常以字符串传输。

## 6. 面试口述版

> 深分页慢在扫描并丢弃大量前置记录，有索引也不能直接跳到第 N 行。必须保留页码时，我用覆盖索引先取 ID 再延迟关联；连续翻页优先用时间加唯一 ID 做游标，保证稳定排序。分布式主键则按规模选择自增、号段、UUID 或 Snowflake，同时考虑索引宽度、时钟和节点号冲突。趋势递增不等于提交有序，唯一 ID 也不等于权限安全。

## 7. 易错点与练习

- 不用 `SELECT *` 当默认分页返回；查询明细、统计总数可以分别优化。
- 不删除重复值来“修复”不稳定排序，而是补唯一排序键。
- 测试至少覆盖同一时间戳、主键空洞、并发插入、排序字段变化、游标筛选变更。
- 比较首页/中间/深页的实际扫描行数与耗时，同时标明冷缓存还是热缓存。
