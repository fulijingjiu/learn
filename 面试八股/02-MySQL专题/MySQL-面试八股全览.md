## 1. ACID

| 字母 | 英文 | 中文 | 一句话 |
|---|---|---|---|
| A | Atomicity | 原子性 | 要么全成功，要么全撤销 |
| C | Consistency | 一致性 | 事务前后数据满足约束（业务+库约束） |
| I | Isolation | 隔离性 | 并发事务互不干扰（靠隔离级别） |
| D | Durability | 持久性 | 提交后断电也不丢（靠 redo 等） |

InnoDB 里常见支撑：undo（回滚/MVCC）、redo（持久化）、锁 + MVCC（隔离）。

### 面试口述版

> ACID 就是原子、一致、隔离、持久。InnoDB 用 undo/redo 和锁、MVCC 来保证。业务上「扣库存+下单」必须放同一事务，避免只成功一半。

## 2. 锁：行锁 / 表锁 / 间隙锁 / 意向锁

| 概念 | 英文 | 要点 |
|---|---|---|
| 行锁 | Row lock | InnoDB 默认尽量锁行，并发好 |
| 表锁 | Table lock | MyISAM 典型；InnoDB 在 DDL、或某些全表操作时也会升到表级 |
| 共享 / 排他 | S / X | 读共享、写排他；X 与其它冲突 |
| 意向锁 | Intention lock（IS/IX） | 表级「信号灯」：表示「我下面有行要加 S/X」，方便快速判断表锁能否加上 |
| 间隙锁 | Gap lock | 锁索引记录之间的间隙，防插入，配合 RR 减幻读 |
| 临键锁 | Next-key lock | 记录锁 + 间隙锁；InnoDB RR 下常见加锁单位 |

加锁还跟「有没有走索引、隔离级别」有关：没索引可能锁更多，甚至接近表级效果。

### 面试口述版

> InnoDB 是行级锁，并发比 MyISAM 的表锁好。RR 下还有间隙锁、临键锁，用来减少幻读。意向锁是表上的标记，让「能不能加表锁」判得快。面试常问：更新没走索引可能锁很多行。

> 细节见：[`MySQL-存储引擎.md`](./MySQL-存储引擎.md)、[`MySQL-事务隔离级别.md`](./MySQL-事务隔离级别.md)

## 3. MVCC（多版本并发控制）

- **MVCC**：Multi-Version Concurrency Control，多版本并发控制。
- 读不一定堵写、写不一定堵读：读的是某个**版本快照**，不是当面抢同一行。
- InnoDB：行里有隐藏列（如事务号、回滚指针），结合 **undo log** 串出版本链；用**读视图 Read View** 判断可见性。
- 和锁配合：快照读（普通 SELECT）走 MVCC；当前读（`FOR UPDATE` / `LOCK IN SHARE MODE` / 更新删除）加锁读最新。

### 面试口述版

> MVCC 就是一行留多个版本，普通 SELECT 读自己事务该看见的版本，所以读写可以并发。InnoDB 靠 undo 链和 Read View。要锁最新行就用当前读，比如 `SELECT ... FOR UPDATE`。

## 4. 回表与覆盖索引

| 概念 | 含义 |
|---|---|
| 回表 | 二级索引叶子只有「索引列+主键」，还要拿主键回聚簇索引取整行 |
| 覆盖索引 | Covering index：查询要的列**都在**二级索引里，不用回表 |

优化思路：联合索引按查询列设计，让 `SELECT` 列表被索引覆盖；或只查主键/索引列。

> 基础见：[`MySQL-聚簇与非聚簇索引.md`](./MySQL-聚簇与非聚簇索引.md)、[`MySQL-最左前缀原则.md`](./MySQL-最左前缀原则.md)

### 面试口述版

> 二级索引找到主键后还要回聚簇树拿整行，叫回表。如果索引已经包含查询需要的所有列，就是覆盖索引，少一次 IO，更快。

## 5. 索引失效常见原因

常见说法（一般情况）：

1. 对索引列做**函数 / 运算 / 类型隐式转换**（如字符串列不加引号）。
2. 联合索引**不满足最左前缀**（跳过左列）。
3. `LIKE '%xx'` **前置模糊**。
4. 条件里 `OR` 连到无索引列（优化器可能放弃）。
5. 使用 `!=` / `NOT IN` / 大量 `OR` 等，优化器可能选全表（视选择率）。
6. 范围条件后，联合索引**后面的列**可能用不上（常见说法）。

排查：看 `EXPLAIN`，看 `key` 是否为预期索引、`type` 是否太差。

### 面试口述版

> 索引失效常见是：列上套函数、类型转换、最左前缀没用上、`LIKE` 百分号在前。别死记条文，用 EXPLAIN 看有没有真正走到索引。

## 6. EXPLAIN 常见 type（从好到差，常见说法）

| type | 含义（口语） |
|---|---|
| system / const | 最多一行，极优 |
| eq_ref | 唯一索引等值，联表时常出现 |
| ref | 非唯一索引等值 |
| range | 索引范围扫（`>`、`BETWEEN`、部分 `IN`） |
| index | 扫整个索引树（比全表强一点） |
| ALL | 全表扫描，最差常见情况 |

还看：`key`（用了哪个索引）、`rows`（估计扫多少行）、`Extra`（如 `Using index` 覆盖索引、`Using filesort`、`Using temporary`）。

### 面试口述版

> EXPLAIN 里我先看 type：尽量别是 ALL；再看 key、rows、Extra。出现 Using index 往往是覆盖索引，好信号；filesort、temporary 要警惕。

## 7. 主从复制（Replication）

- 常见链路：**主库写 binlog → 从库 IO 线程拉 relay log → SQL 线程回放**。
- 作用：读写分离、备份、高可用底座。
- 注意：默认多为**异步**，主从可能短暂延迟；有半同步等增强（视版本与配置）。
- 面试常提：复制格式 STATEMENT / ROW / MIXED；GTID 便于故障切换（常见说法）。

### 面试口述版

> MySQL 主从靠 binlog：主库记日志，从库拉过来重放。用来读写分离和备份，但异步下从库可能落后，读从库要接受延迟。

## 8. 分库分表思路

何时考虑：单表过大（行数/容量）、写热点、连接打满——先优化索引与架构，再拆。

| 方式 | 思路 |
|---|---|
| 垂直拆分 | 按业务拆库/拆列（宽表拆冷热） |
| 水平拆分 | 按规则拆行：取模、范围、雪花/订单号路由 |
| 中间件 | ShardingSphere、Vitess 等（常见选型） |

难点：跨库事务、跨片 JOIN、全局唯一 ID、扩容迁移、分页排序。

### 面试口述版

> 先优化再拆。垂直按业务拆，水平按用户 ID 或订单号取模。难点是分布式事务、跨库查询和扩容。能用读写分离和缓存解决的，别急着上分片。

## 9. 慢 SQL 排查

1. 开 **慢查询日志 slow query log**（或云监控）。
2. `EXPLAIN` / `EXPLAIN ANALYZE`（版本支持时）看计划。
3. 看有没有索引、是否回表过多、是否临时表/文件排序。
4. `SHOW PROCESSLIST` 看当前卡住谁。
5. 业务侧：少 `SELECT *`、控制深分页、避免大事务、注意 N+1。

### 面试口述版

> 慢 SQL 先找慢日志，再 EXPLAIN。优先加对索引、避免全表和深分页。大事务和 `SELECT *` 也是常见坑。
