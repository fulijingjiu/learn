# MySQL：一条 SQL 的执行过程

> 范围：MySQL 8.0 / 8.4 + InnoDB。先学物理执行链路，再区分 SQL 的逻辑处理顺序；两者不是同一道题。

## 1. 概念与为什么：先分 Server 层、引擎层

```text
应用 / 连接池
  → 连接与会话（认证、会话设置）
  → 解析与预处理（语法、表列解析等）
  → 优化器（选访问路径、连接顺序与算法）
  → 执行器（按计划调度迭代器、调用引擎）
  → InnoDB（索引、页、Buffer Pool、MVCC、锁、日志）
  → 结果经协议返回应用
```

Server 处理 SQL 共性，引擎负责数据如何存取。权限检查会涉及连接和语句执行等阶段，不能把所有权限校验死记成“第一步只查一次”。连接池能减少反复建连成本，但池满时也会排队。

**版本边界**：MySQL 8.0 已移除 Server 层的 Query Cache。查询反复执行更快，可能是页已在 Buffer Pool、OS 缓存、应用缓存命中，不是每条 SQL 都先查“结果缓存”。

## 2. 用查询走一遍

假设 `orders` 有主键 `id` 和联合索引 `(user_id, created_at, id)`：

```sql
SELECT id, created_at
FROM orders
WHERE user_id = 42
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

| 环节 | 在这条 SQL 中干什么 | 常见问题 |
|---|---|---|
| 连接 | 复用或新建连接，确定库、账号、会话时区等 | 连接池等待、TLS、认证失败 |
| 解析/预处理 | 识别关键字，确认表、字段、类型等是否合法 | 语法错、列名错、权限错 |
| 优化 | 比较联合索引与其他路径，估计行数和成本 | 统计信息偏差、选择率估错 |
| 执行 | 按计划取记录、过滤，满足 LIMIT 后停止可停止的上游工作 | 扫描过多、排序/临时结果很大 |
| InnoDB | 在 B+ 树定位，通过缓存页或磁盘取记录，检查版本可见性 | 冷缓存、随机 IO、长事务旧版本 |
| 返回 | 编码、传输、客户端反序列化 | 大结果集、网络慢、ORM 映射慢 |

这个查询可能按联合索引反向扫描，并被索引覆盖，因此不必为输出字段取整行。**实际仍以计划为准**；索引存在不代表优化器一定选它，也不代表所有一致性检查都零额外访问。

## 3. 更新比查询多了什么？

```sql
START TRANSACTION;
UPDATE stock SET available = available - 1
WHERE sku_id = 1001 AND available > 0;
COMMIT;
```

1. 同样经过解析、优化、执行；假设 `sku_id` 是唯一索引，可定位目标记录。
2. InnoDB 对写入记录加相应锁，检查条件；遇到并发事务可能等待，不能按普通快照读来理解更新。
3. 修改 Buffer Pool 中的数据和相关索引，产生 undo 与 redo；Server 为事务积累 binlog 事件。
4. 提交时协调引擎日志与 binlog；数据文件里的页可以稍后刷盘。
5. 应用必须看受影响行数：为 0 可能是无该 SKU，也可能是库存不足，要按业务区分。

这里减少库存使用数据库条件更新，避免“先普通 SELECT 再把旧值写回”的丢失更新问题。事务中不要夹用户等待、远程支付、长时间 HTTP 调用。

详细日志时序见 [redo / binlog 与两阶段提交](./MySQL-redo-binlog与两阶段提交.md)。

## 4. 逻辑顺序 ≠ 执行计划

便于理解语义的常见顺序：

```text
FROM / JOIN / ON → WHERE → GROUP BY → HAVING
→ 窗口计算等 → SELECT → DISTINCT → ORDER BY → LIMIT
```

它解释了 WHERE 通常不能直接引用本层 SELECT 别名，而 HAVING/ORDER BY 在 MySQL 中有别名支持。但优化器会下推条件、重排符合条件的连接、选择索引，**不是机械地按文本顺序建一堆中间表**。CTE、窗口函数等也有自己的语义约束。

## 5. 慢在哪里，证据怎么找？

| 现象 | 先拿什么证据 | 下一步 |
|---|---|---|
| 应用请求慢，但单独执行 SQL 快 | 连接池等待、连接建立、ORM 与网络耗时 | 分段打点，不只盯 SQL |
| SQL 扫很多行 | 慢日志、`EXPLAIN` 的 key/rows/filtered | 看索引与筛选是否匹配 |
| 估计只几行，实际很多 | 测试环境 `EXPLAIN ANALYZE` | 对比估算与 actual rows / loops |
| 一条 UPDATE 卡住 | 当前事务、锁等待关系 | 先找阻塞源，再看事务为何不结束 |
| COMMIT 慢 | 日志同步耗时、磁盘延迟、半同步等待 | 查提交路径，不先乱加查询索引 |

`EXPLAIN` 通常展示估计计划，`EXPLAIN ANALYZE` **会实际执行查询**并测量；应先在测试环境用受控 SELECT，不能把它当对任何 SQL 都无副作用的命令。`Using filesort` 代表额外排序，不必然落磁盘；`ALL` 也不是永远错误，小表或大比例读取可能本就适合扫描。

## 6. 面试口述版

> SQL 先经过连接和会话，再解析预处理、优化，执行器按照计划调用存储引擎。InnoDB 用索引、Buffer Pool、MVCC 或锁拿数据，结果还要经过网络返回。更新额外涉及行锁、undo、redo、binlog 和提交协调。MySQL 8 已没有 Query Cache，排慢 SQL 时我会把连接等待、执行、提交、传输分别测量。

## 7. 易错点与练习

- SQL 文本中 `WHERE a=1 AND b=2` 的书写先后，不决定联合索引必须按这个顺序；看索引列顺序与条件类型。
- 二级索引查整行可能回表；覆盖索引和 ICP 是不同优化，不要都解释成“不回表”。
- 普通 SELECT 在 RC/RR 下通常是一致性读，但还会拿元数据锁；“完全不碰任何锁”不准确。
- 练习：对同一业务查询分别只选索引列、再加一个未覆盖的大字段，记录计划、扫描量、返回字节数。一次只改一个变量，不承诺固定提升倍数。
