# MySQL：类型选型与 DDL 注意点

> 范围：MySQL 8.0 / 8.4、InnoDB。这些行为不能直接套到 PostgreSQL / SQL Server，尤其是 DDL 是否可在用户事务里回滚。

## 1. 概念与为什么：类型决定语义，也影响索引与迁移

字段不是“能塞进去就行”：金额精度、时间语义、排序规则、字符长度、NULL 含义、未来范围，都应在建表时明确。列越宽，页和索引越占空间；错误类型还会造成隐式转换与查询计划变化。

## 2. CHAR 与 VARCHAR

| 项目 | CHAR(n) | VARCHAR(n) |
|---|---|---|
| 逻辑长度 | 定长字符列，通常涉及空格填充/尾空格处理 | 变长字符列，保存实际长度并带长度信息 |
| 常见场景 | 真正固定长度代码 | 昵称、标题等长度变化内容 |
| n 的单位 | 字符数，不等于固定 n 字节 | 字符数，不等于最多只用 n 字节 |
| 注意 | 字符集、行格式、SQL mode、collation 影响具体行为 | 行大小限制、最大字节数、索引长度也要核算 |

`utf8mb4` 一个字符可能占多个字节。不要简单说“CHAR 一定快”“VARCHAR(255) 只有 255 字节”。文本标识是否区分大小写/重音、是否把尾空格视为相同，要看 collation；外部编号、校验值可考虑明确的二进制语义。emoji 用 `utf8mb4`，不把老的 utf8 别名当完整 Unicode 支持。

## 3. 金额与 ID 类型

- 金额常用 `DECIMAL(p,s)`，p 为总精度，s 为小数位，例如 `DECIMAL(12,2)`；它是精确十进制表示，不是 FLOAT/DOUBLE 的近似二进制浮点。
- 也可用 BIGINT 存最小货币单位，但要统一币种、小数尺度、溢出及舍入规则，不能所有币种都假设“两位小数”。
- Java 对应 BigDecimal、Python 对应 Decimal；不要先转浮点丢精度后再转回。
- 主键 INT/BIGINT 看容量与增长速度；不要把 INT(11) 的显示宽度当可存 11 位数字的容量。
- NULL 是未知/缺失，不是空字符串或 0；是否 NOT NULL 应服从业务语义，不是只为“索引一定更快”。

## 4. DATETIME 与 TIMESTAMP

| 维度 | DATETIME | TIMESTAMP |
|---|---|---|
| 核心语义 | 保存日期时间值；不按会话时区自动做读写转换 | 写入按会话时区转成内部 UTC 时间点，读取转回会话时区 |
| 常见范围 | 约 1000–9999 年 | MySQL 8.4 的通常范围约 1970–2038 年 |
| 小数秒 | 可指定 0–6 位精度 | 同样可指定 0–6 位精度 |
| 自动创建/更新 | 可显式配置 DEFAULT / ON UPDATE | 同样应显式配置，不能仅看类型推断 |

- `DATETIME` 不携带时区，不等于“它天然就是北京时间/UTC”；如果约定存 UTC，需要应用与连接统一执行该约定。
- `TIMESTAMP` 不是数据库自动保存“用户原始时区名称”。若业务要知道用户的本地日程语义，可另存时区标识。
- `ON UPDATE CURRENT_TIMESTAMP` 的行为来自列定义，不是所有 TIMESTAMP 都自动变；两种类型都支持相应配置。
- 连接池每个连接的 `time_zone`、应用序列化规则和前端展示规则要一致。查看：`SELECT @@session.time_zone, @@global.time_zone;`。
- 报表按天聚合，先确定“哪一个时区的一天”。例如页面显示统一标注 Asia/Shanghai（UTC+8），不能把未带时区的字符串直接当跨系统时间点。

## 5. DELETE / TRUNCATE / DROP 对比

| 项目 | DELETE | TRUNCATE TABLE | DROP TABLE |
|---|---|---|---|
| 目的 | 按条件删行 | 清空整表，保留表结构定义 | 删除表对象与数据 |
| WHERE | 支持 | 不支持 | 不适用 |
| MySQL 用户事务回滚 | InnoDB 普通 DML，未提交时可回滚 | DDL，隐式提交，不能靠 ROLLBACK 撤销 | 普通表 DDL，隐式提交，不能靠 ROLLBACK 撤销 |
| 自增值 | 通常不重置 | 通常重置到起始值 | 表已不存在 |
| DELETE 触发器 | 按删除行触发 | 不触发 DELETE 触发器 | 不是逐行 DELETE |
| 日志 | 行删除、undo/redo/binlog 等有成本 | 有 DDL 日志/复制事件，不是“不记任何日志” | 有 DDL 相关日志/复制记录 |

TRUNCATE 通常通过重建空表/表空间路径实现，不逐行删，因此常比全量 DELETE 快；但它需要相应权限，受外键等限制，破坏性也更大。

**原子 DDL 不等于事务性 DDL**：支持的 DDL 在崩溃时可保证内部全成或全不成，并不代表用户能 `BEGIN; TRUNCATE...; ROLLBACK;` 把内容还原。也不要认为 DELETE 后文件立即缩小、空间必还给操作系统，实际取决于表空间和回收方式。

## 6. 大表变更与大批删除：先控风险

### 大表加列/索引

1. 查看版本、表结构、数据量、磁盘余量、复制状态，列出 DDL 的目标。
2. 核对该操作是否支持 `INSTANT` / `INPLACE` / `COPY` 及允许的锁级别；不是所有 `ADD COLUMN` 都能瞬间完成。
3. 在线 DDL 也可能需要短暂元数据锁，旧长事务会让 DDL 排队，还可能阻塞后续请求。
4. 预演耗时、空间、主从延迟、失败退出与回滚/恢复方案。先兼容式发布，再移除旧列，避免应用与表结构版本错配。

### 大批量删除

先用同样 WHERE 做预览，确认命中范围、索引和备份。按稳定主键/时间窗口小批提交，观察锁、日志量、复制延迟和磁盘，而不是一次长事务删数千万行。分批并不自动等于业务原子；要求整批全成全败时必须重新设计方案。软删除也会占空间并影响唯一性/查询条件，不能代替归档策略。

本文只给检查步骤，不提供对未知真实表可直接执行的一键清空脚本。

## 7. 面试口述版

> 类型选型先看语义：金额用精确十进制或统一尺度的整数，字符串同时看字符集和排序规则。DATETIME 不自动按会话时区转换，TIMESTAMP 会转换，两者自动更新都要看显式列定义。DELETE 是可事务回滚的行删除，MySQL 普通表的 TRUNCATE 和 DROP 是会隐式提交的 DDL。大表在线变更也有元数据锁与复制压力，要先验证算法、空间和恢复方案。

## 8. 易错点

- 不把其他数据库的 TRUNCATE 回滚行为照搬到 MySQL。
- 不认为“DDL 只改元数据所以完全不阻塞”“加个字段肯定无风险”。
- 不使用浮点比较金额；也不把日期、数字都塞 VARCHAR 后到处 CAST。
- 所有破坏性操作先确认库、表、条件、受影响范围、备份与审批，不让 AI 按猜测直接执行。
