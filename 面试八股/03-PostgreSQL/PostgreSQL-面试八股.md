# PostgreSQL 面试八股

> 学习笔记 · 面试八股  
> 重点：和 MySQL 的差异 + 高频口述。  
> 对照总览：[`00-数据库总览-关系型对比.md`](./00-数据库总览-关系型对比.md) · [`三库对比速查.md`](./三库对比速查.md)

---

## 1. 一句话定位

PostgreSQL（常称 **PG**）是功能很强的**开源关系型数据库**：标准 SQL 好、扩展多、复杂查询与 JSON/GIS 出名。默认隔离级别一般是 **读已提交 Read Committed（RC）**。

### 面试口述版

> PG 是开源里偏「全能」的关系库，复杂 SQL、JSONB、扩展生态强；默认 RC。互联网业务 MySQL 更常见，但要分析型 SQL 或 GIS 很多人选 PG。

---

## 2. 与 MySQL 差异总表（常见说法）

| 维度 | PostgreSQL | MySQL（InnoDB） |
|---|---|---|
| 默认隔离 | RC | RR |
| MVCC 清理 | 更新产生新版本，旧版本靠 **VACUUM** 回收 | undo 集中管理，purge 清理 |
| 表存储 | 堆表 + 索引；更新常「新元组」 | 聚簇索引组织表（主键叶子是数据） |
| 索引种类 | B-Tree 默认；还有 **GIN / GiST / BRIN / Hash** 等 | 常见以 B+Tree 为主；全文等另说 |
| JSON | **JSON / JSONB**（JSONB 可索引、二进存储，更常用） | JSON 类型有，生态与操作习惯不同 |
| 扩展 | Extension 多（PostGIS 等） | 插件引擎、插件有，但「扩展语言/类型」叙事弱于 PG |
| 连接模型 | 多进程：一个连接常对应一个后端进程 | 常见线程模型（视实现） |
| 自增 | **SEQUENCE**（序列）；`GENERATED ... AS IDENTITY` / `serial` 常见说法 | `AUTO_INCREMENT` |
| 复制 | 流复制等；逻辑复制也常见讨论 | binlog 主从 |

---

## 3. MVCC 与 VACUUM

- PG 也是多版本：更新/删除不立刻抹掉旧行，新事务按快照看该看的版本。
- 旧版本占空间，需要 **VACUUM**（清理）和相关自动机制（如 autovacuum）回收；还有 **VACUUM FULL** 等更重的整理（会锁表，生产慎用——常见说法）。
- 面试常问：为什么表变「胀」？→ 更新多 + VACUUM 跟不上。

### 面试口述版

> PG 的 MVCC 会留下旧版本行，靠 VACUUM 回收。更新很频繁时如果清理不及时，表会膨胀、计划变差。这是和 MySQL「undo 链」叙事不一样的地方。

---

## 4. 索引种类（常考名）

| 索引 | 英文 | 适合（口语） |
|---|---|---|
| B-Tree | B-Tree | 默认；等值、范围、排序 |
| GIN | Generalized Inverted Index | 数组、全文、**JSONB 包含查询** 等 |
| GiST | Generalized Search Tree | 几何、范围类型、近似搜索等 |
| BRIN | Block Range Index | 很大、天然有序的表，索引很小 |
| Hash | Hash | 等值（场景相对窄，常见说法） |

### 面试口述版

> PG 默认 B-Tree。查 JSONB、数组常用 GIN；地理和一些范围类型常提 GiST。这是相对 MySQL「索引种类更丰富」的加分点。

---

## 5. JSON / JSONB

- **JSON**：文本存储，写入原样保留。
- **JSONB**：二进制存储，可建索引、查询通常更合适业务检索——**一般更推荐 JSONB**（常见说法）。
- 可配合 GIN 做包含、键存在等查询。

### 面试口述版

> 要落库又要按字段查，我优先 JSONB，需要时加 GIN。只当文档存、很少按键查，用 JSON 也行。

---

## 6. 事务与隔离

- 支持常见隔离级别；**默认 RC**。
- 也可设 RR、Serializable；PG 的 Serializable 有自己的实现思路（SSI 等，面试点到即可）。
- 事务块：`BEGIN` / `COMMIT` / `ROLLBACK`；有丰富的约束与 CTE。

### 面试口述版

> PG 默认读已提交。要可重复读或串行化可以改，但默认 RC 下「同语句内一致、跨语句可能变」要心里有数。

---

## 7. 连接与进程模型

- 常见说法：每个客户端连接对应一个 **backend 进程**（另有相关辅助进程）。
- 连接很多时内存与进程开销明显 → 生产常用 **连接池**（PgBouncer 等）。

### 面试口述版

> PG 是多进程模型，连接数飙高要上连接池，这和 MySQL 线程模型的运维关注点不太一样。

---

## 8. 序列与自增

- **SEQUENCE**：独立序列对象，`nextval` 取号。
- 表字段可用 `serial` / `bigserial`（常见写法）或标准 **IDENTITY** 列（视版本与习惯）。
- 注意：序列取值一般**不回滚**（事务回滚号也可能空掉）——面试常提。

### 面试口述版

> PG 用序列做自增，回滚事务也可能跳号，别用连续序号当业务强假设。

---

## 9. 复制（概念级）

- **物理流复制**：主库 WAL 流到从库，做热备/读写分离底座。
- **逻辑复制**：按逻辑变化订阅，灵活但场景与限制要单独评估。
- 面试说到「主从延迟、只读从库」即可，不必背参数名。

### 面试口述版

> PG 常用流复制做高可用和只读扩展；和 MySQL binlog 主从是同一类问题，实现不一样。

---

## 10. 高频问答速背

**Q：为什么选 PG 不选 MySQL？**  
> 要复杂 SQL、窗口函数、GIS、JSONB 索引、自定义扩展；团队认准开源标准 SQL。

**Q：PG 和 MySQL 索引组织最大差别？**  
> MySQL InnoDB 主键聚簇；PG 是堆表+索引，二级索引指向元组标识，更新多时还要关心 VACUUM。

**Q：JSONB 为什么常用？**  
> 可索引、查询灵活，适合半结构化又要条件过滤的数据。
