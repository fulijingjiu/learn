## 1. 先读表结构（分析任何问题的第一步）

**步骤**

1. 有哪些表、主键、唯一约束、外键（若有）。  
2. 有哪些索引、列顺序（联合索引最左列是谁）。  
3. 字段类型、是否可空、默认值、注释。  
4. 大约多少行、数据量级（决定能不能全表扫）。

**常用命令（示意）**

| 目的 | MySQL | PostgreSQL | SQL Server |
|---|---|---|---|
| 表结构 | `SHOW CREATE TABLE t;` / `DESC t;` | `\d+ t`（psql） | `sp_help 't'` / 查系统视图 |
| 索引 | `SHOW INDEX FROM t;` | `\di` / 查 `pg_indexes` | 查 `sys.indexes` |
| 行数约数 | `SHOW TABLE STATUS` / `information_schema` | `pg_class.reltuples` | 统计视图 / 近似行数 |

**口述短句**

> 分析先看结构：主键、索引列顺序、类型和大概行数；没有地图就别急着改 SQL。

## 2. EXPLAIN / 执行计划怎么看（抓重点）

### MySQL：`EXPLAIN` / `EXPLAIN ANALYZE`（高版本）

优先看：

| 字段 | 想确认什么 |
|---|---|
| `type` | 访问方式：`const`/`eq_ref`/`ref` 较好；`range` 可接受；`ALL` 全表扫要警惕 |
| `key` | 实际用了哪个索引；`NULL` 往往没走索引 |
| `rows` | 估算扫描行数；越大越可疑 |
| `Extra` | `Using filesort` / `Using temporary` 可能贵；`Using index` 常表示覆盖索引 |

**步骤**

1. 对慢 SQL 跑 `EXPLAIN`。  
2. 问：有没有该用的索引？`rows` 是否爆炸？有没有临时表/文件排序？  
3. 改条件/索引后再 `EXPLAIN` 对比。  
4. 条件允许用 `EXPLAIN ANALYZE` 看真实耗时（注意生产影响）。

### PostgreSQL：`EXPLAIN (ANALYZE, BUFFERS)`

- 看 **实际行数 vs 估算行数**是否差很多 → 统计信息可能过期。  
- 看 Seq Scan vs Index Scan、是否 Hash/Sort 过重。

### SQL Server：实际执行计划（SSMS）/ `SET STATISTICS IO, TIME ON`

- 看是否 Index Seek / Scan、预估与实际行数、关键警告（如 Implicit Conversion）。

**口述短句**

> 执行计划先看：用没索引、扫多少行、有没有临时表/排序；改完再对比计划，用数据说话。

## 3. 统计信息（优化器「猜得准不准」）

- 优化器靠统计信息估行数；过期会导致选错索引或误走全表。  
- MySQL：InnoDB 有持久统计；可 `ANALYZE TABLE t;`。  
- PG：`ANALYZE t;`；长期靠 autovacuum/autoanalyze。  
- SQL Server：自动更新统计；也可手动 `UPDATE STATISTICS`。

**何时想到统计**

- 计划里估算行数离谱；刚导完大批数据；升级/迁移后变慢。

**口述短句**

> 计划离谱时先怀疑统计过期，对相关表做分析/更新统计，再重新看计划。

## 4. 采样查询（先摸数据长什么样）

**清单（注意：生产只读、加 LIMIT、避开高峰）**

```sql
-- 总量级（大表慎用精确 COUNT，可先近似或抽样）
SELECT COUNT(*) FROM orders;  -- 大表可能很慢

-- 分布
SELECT status, COUNT(*) FROM orders GROUP BY status;

-- 极值 / 空值
SELECT MIN(created_at), MAX(created_at),
       SUM(col IS NULL) AS null_cnt  -- MySQL 写法示意
FROM orders;

-- 抽样几行看脏数据
SELECT * FROM orders ORDER BY id DESC LIMIT 20;
```

**技巧**

- 先抽样、看分布，再写「全量核对」SQL。  
- 大表 `COUNT(*)` / 无索引 `GROUP BY` 可能拖库 → 用从库、近似、或离线数仓。

**口述短句**

> 先小样本看分布和脏数据，再决定索引和核对 SQL；大表聚合优先在从库或离峰。

## 5. 慢查询日志（找到「谁在拖」）

**思路**

1. 打开慢查询日志（或云监控里的慢 SQL）。  
2. 按耗时 / 次数排序，抓 Top SQL。  
3. 拿完整 SQL（含参数形态）去 `EXPLAIN`。  
4. 区分：偶发大报表 vs 高频小慢查询（后者往往更伤）。

**MySQL 常见点**

- `long_query_time`、`slow_query_log`；可用 `pt-query-digest` 之类汇总（运维工具，了解即可）。

**口述短句**

> 慢日志找 Top SQL，按「次数×耗时」看伤害；再对单条做执行计划，而不是凭感觉加索引。

## 6. 用 SQL 做简单数据核对

**常见核对场景**

| 场景 | 思路 |
|---|---|
| 主从表不一致 | 订单数 vs 明细行数；金额合计是否相等 |
| 迁移/同步 | 两边 `COUNT`、关键字段 checksum/抽样对比 |
| 重复数据 | `GROUP BY uk HAVING COUNT(*)>1` |
| 孤儿行 | `LEFT JOIN ... WHERE 右表.id IS NULL` |
| 状态机异常 | 不允许的状态组合用 `WHERE` 列出 |

**步骤**

1. 定义「正确」规则（业务一句话）。  
2. 写成可重复跑的核对 SQL。  
3. 先在从库/备份跑；限制结果集。  
4. 把异常主键导出，再逐条追业务日志。

**口述短句**

> 核对先写清业务规则，再落成可重复 SQL；先找异常主键列表，再回业务侧定位。

## 7. 分析流程总清单

1. [ ] 表结构 + 索引列顺序清楚了  
2. [ ] 数据量级、关键列分布摸过样  
3. [ ] 慢 SQL / 问题 SQL 有完整文本  
4. [ ] `EXPLAIN`（或等价）看过，记下 type/key/rows  
5. [ ] 统计信息是否需要刷新已判断  
6. [ ] 改动有前后对比（计划或耗时）  
7. [ ] 生产操作：只读优先、有窗口、有回滚方案
