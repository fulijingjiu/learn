# 实战 · 用 AI 辅助数据库工作

> 怎么提问、给哪些上下文、让 AI 写 SQL/改索引/读计划、你必须自己核对什么、安全红线。  
> 搭配：[`分析数据`](./实战-分析数据.md) · [`排查故障`](./实战-排查故障定位错误.md) · [`开发技巧`](./实战-开发实现技巧.md)

---

## 1. AI 适合干什么、不适合干什么

| 适合 | 不适合当唯一依据 |
|---|---|
| 起草 SQL、改写可读性 | 未经验证就上生产 |
| 解释报错、解释 `EXPLAIN` 字段含义 | 凭聊天记录当容量规划结论 |
| 根据表结构提索引候选 | 代替你理解业务约束与事务边界 |
| 生成核对 SQL、测试数据 | 处理真实隐私数据内容本身 |
| 对比 MySQL/PG/SQL Server 语法差异 | 保证某云厂商专有语法 100% 正确 |

**口述短句**

> AI 是副驾驶：加速草稿和解释；上线前的正确性、性能和安全仍由人用计划与环境验证。

---

## 2. 怎么提问（结构清楚，答案才稳）

**推荐提问模板**

1. **目标**：我要什么（慢查询优化 / 写核对 SQL / 解释死锁）。  
2. **环境**：MySQL 8 / PG 14 / SQL Server 某版本；大概数据量。  
3. **表结构**：`CREATE TABLE` 或关键列 + 索引。  
4. **现状**：慢 SQL 原文、`EXPLAIN` 结果、报错全文。  
5. **约束**：能否加索引、能否改 SQL、是否必须兼容旧版本。  
6. **期望输出**：只要改写 SQL / 只要索引建议 / 要分步排查清单。

**反例**

- 「这个查询好慢怎么办？」（无表结构、无计划、无数据量）  
- 「帮我设计一下数据库。」（无业务实体与访问模式）

## 3. 该给 AI 哪些上下文

**可以给（优先脱敏）**

- 表结构：`CREATE TABLE`、索引定义。  
- 脱敏后的 SQL；参数用占位或假数据。  
- `EXPLAIN` / `EXPLAIN ANALYZE` 文本（可打码库名）。  
- 报错**全文**（错误码 + 消息）。  
- 隔离级别、是否主从、是否分库（若相关）。  
- 「业务规则一句话」（例如：订单取消必须库存加回）。

**不要给**

- 生产密码、连接串里的密钥、Token。  
- 真实姓名、手机、身份证、完整地址、银行卡等隐私。  
- 未授权的生产数据导出全文。  
- 内网地址与未公开的安全架构细节（按公司规定）。

**脱敏示例**

- `user_id=13800138000` → `user_id=10001`  
- 真实邮箱 → `user@example.com`  
- 连接串只留 `jdbc:mysql://***:3306/app_db`

## 4. 让 AI 写 SQL / 改索引 / 读计划的正确姿势

### 写 SQL

1. 先给表结构 + 业务规则。  
2. 要求：参数绑定风格、标明数据库方言、说明假设。  
3. 你在测试库跑通：结果集对不对、有无全表扫。  
4. 再考虑进应用（ORM/XML）。

### 改索引

1. 给现有索引 + 慢 SQL + `EXPLAIN`。  
2. 让 AI 给出「候选索引」和「可能副作用」（写放大、空间）。  
3. 你在测试环境加索引，对比计划与写入耗时。  
4. 一次改一处，便于回滚。

### 解读执行计划

1. 粘贴完整计划文本。  
2. 问：主要成本在哪、是否索引失效、估算行数是否可疑。  
3. 对照 [`分析数据`](./实战-分析数据.md) 自己再看一遍 `type`/`key`/`rows`。

**口述短句**

> 给结构、SQL、计划三件套，让 AI 出草案；自己在测试库用执行计划和结果集验收。

---

## 5. 必须自己核对的点（清单）

- [ ] SQL 语义是否符合业务（尤其 DELETE/UPDATE 的 WHERE）  
- [ ] 是否参数化，有无拼接注入  
- [ ] 事务边界是否仍正确  
- [ ] 索引是否破坏最左前缀、是否重复多余  
- [ ] 深分页、`SELECT *`、大 `IN` 是否可接受  
- [ ] 三库语法是否用错（LIMIT vs OFFSET/FETCH 等）  
- [ ] 生产执行窗口、锁影响、是否先在从库/备库验证  
- [ ] AI 引用的「版本特性」是否真的存在于你的版本

## 6. 排查故障时怎么用 AI

**好用法**

- 「根据这条报错全文，列出可能原因与排查顺序。」  
- 「根据这段 InnoDB STATUS 死锁片段，解释等待双方在锁什么。」  
- 「把我的排查笔记整理成复盘模板。」

**坏用法**

- 把生产库账号交给 AI 工具「直接连上去看」（除非公司明确允许且走安全通道）。  
- 不看证据，只按 AI 说的在生产 `KILL` 或删数据。

**步骤建议**

1. 你按 [`排查故障`](./实战-排查故障定位错误.md) 取证。  
2. 把脱敏证据交给 AI 整理假设。  
3. 你选择低风险步骤验证。  
4. 结果再反馈给 AI 收窄（多轮，但你掌控执行）。

---

## 7. 安全红线（背下来）

1. **不贴生产密码、密钥、完整连接串。**  
2. **不贴真实隐私行数据；结构可以用，内容要假。**  
3. **不让 AI 的 SQL 未经审查直接在生产执行。**  
4. **破坏性语句（DROP/TRUNCATE/无 WHERE 的 DELETE）默认拒绝，除非你明确要且有备份。**  
5. **公司规定优先**：有的环境禁止把任何生产 schema 贴进公网模型。

**口述短句**

> 给 AI 结构与脱敏现象，不给密钥和真数据；所有写操作必须人审，生产先备份再变更。

---

## 8. 面试怎么说「我用 AI」

> 我用 AI 辅助写 SQL 草案和解释执行计划，但上线前会自己看 EXPLAIN、在测试库验证，敏感信息脱敏，不把生产凭证交给工具。

---

## 9. 一页纸工作流

```
问题 → 脱敏上下文（结构+SQL+计划/报错）
     → AI 草案（SQL/索引/排查步骤）
     → 人审清单（语义/安全/性能）
     → 测试库验证
     → 再上线 / 再取证迭代
```
