## 1. 建表规范（先定规矩，少返工）

**清单**

- 引擎：MySQL 业务表用 **InnoDB**；别新建 MyISAM。
- 主键：尽量有明确主键；常用自增 / 雪花等；避免无业务意义、会变的字段当主键。
- 字符集：MySQL 常用 `utf8mb4` + 合理排序规则（如 `utf8mb4_unicode_ci`）；别用旧的 `utf8`（最多 3 字节）。
- 字段：能 `NOT NULL` 就别滥 `NULL`；金额用 `DECIMAL`，别用 `FLOAT`；时间用 `DATETIME`/`TIMESTAMP` 并统一时区策略。
- 命名：表/列小写+下划线；状态用小整型或短字符串枚举，文档写清含义。
- 必备列：很多业务表会加 `created_at` / `updated_at`；软删用 `deleted_at` 或 `is_deleted`（查时记得过滤）。

**口述短句**

> 建表先定主键、字符集、非空和金额/时间类型；业务表 InnoDB；预留创建/更新时间，后面联查和排查都省事。

## 2. 索引设计（为查询服务，不为「感觉」服务）

**步骤**

1. 列出高频 `WHERE` / `JOIN` / `ORDER BY` / `GROUP BY`。
2. 等值多、区分度高的列优先；联合索引按「最左前缀」排（见专题）。
3. 能覆盖查询就做覆盖索引，少回表。
4. 上线后用 `EXPLAIN` / 慢日志验证，别一次加十几个「以防万一」的索引。

**避坑**

- 索引不是越多越快：写放大、空间涨、优化器更难选。
- 对列做函数/隐式类型转换 → 索引常失效（`WHERE DATE(col)=...`、字符串和数字比）。
- 低区分度列单独建索引收益差（如只有 0/1 的状态），可放联合索引右侧。

**口述短句**

> 索引跟着真实查询走：联合索引守最左前缀，避免函数破坏索引；用执行计划确认，而不是凭感觉加。

## 3. 事务边界（越小越好，但仍要包住一致性）

**该包进同一事务的**

- 「扣库存 + 写订单」这类必须同成同败的多表写。
- 先读后写且依赖一致性时，想清楚隔离级别与锁（必要时 `SELECT ... FOR UPDATE`）。

**不该做的**

- 事务里调外部 HTTP、发短信、大文件上传（拖长锁、易超时）。
- 大事务扫全表改几十万行（拆批、离峰、可回放）。

**步骤口诀**

1. 开启事务 → 2. 只做必要读写 → 3. 尽快提交/回滚 → 4. 外部副作用放到提交后（或用消息表/outbox）。

**口述短句**

> 事务只包住必须原子的多步写；别在事务里做远程调用；大更新拆批，避免长事务锁表拖垮库。

## 4. 分页（深分页是常见坑）

| 写法 | 说明 |
|---|---|
| `LIMIT offset, size`（MySQL） | 简单；**offset 很大时很慢**（仍要扫过前面的行） |
| `OFFSET/FETCH`（SQL Server / 标准） | 同理，深分页贵 |
| 键集分页（seek） | `WHERE id > last_id ORDER BY id LIMIT n`：适合「下一页」，快 |

**技巧**

- 列表优先「上一页/下一页」+ 上次最后一条主键/排序键。
- 必须跳页时：限制最大页码，或先查主键再回表。

**口述短句**

> 浅分页用 LIMIT 即可；深分页改成按上次主键往后翻，避免巨大 OFFSET。

## 5. 批量写入

**清单**

- 多行一次 `INSERT INTO t (c1,c2) VALUES (...),(...),...`，比循环单条快一个数量级。
- 单批别太大（常见几百～几千行一试，看包大小与超时）。
- 需要幂等：用唯一键 + `ON DUPLICATE KEY` / `INSERT ... ON CONFLICT`（PG） / `MERGE`（SQL Server）等，按库选。
- 大批量导入：考虑关闭部分检查、用专用导入工具（仍要在测试环境验证），业务高峰慎用。

**口述短句**

> 批量用多值 INSERT 或库自带 upsert；控制单批大小；靠唯一约束做幂等，而不是先查再插。

## 6. 防 SQL 注入

**必须**

- 永远用**预编译 / 参数绑定**（PreparedStatement、`?` 占位、ORM 参数），用户输入当数据不拼接进 SQL 字符串。
- 动态表名/列名不能参数化时：用白名单映射，禁止直接拼用户字符串。

**不要**

- `"SELECT * FROM u WHERE name='" + name + "'"`  
- 把「转义一下」当唯一防线。

**口述短句**

> 防注入核心是参数绑定；表名列名走白名单；绝不把用户输入拼进 SQL。

## 7. 连接池

**要点**

- 应用用连接池（HikariCP、Druid 等），别每次请求新建连接。
- 配：`最大连接数`、超时、空闲回收；**池大小 ≠ 越大越好**（受 DB `max_connections` 与机器数限制）。
- 多实例：`实例数 × 每池最大连接` 要小于库可承受连接。
- 借出连接务必归还（try-with-resources / 框架托管）；泄漏表现为连接耗尽、新请求卡住。

**口述短句**

> 用连接池并限制总量；多实例时算总连接数；防止连接泄漏比盲目加大池更重要。

## 8. ORM 注意点（MyBatis / JPA / EF 等）

**清单**

- 清楚「这条 ORM 最终发出什么 SQL」：打开 SQL 日志，对复杂查询手写 SQL/XML 往往更稳。
- 避免 N+1：循环里按 id 查 → 改成一次 `IN` 或 join / 批量。
- 懒加载：在事务外访问关联可能报错或打出意外查询。
- 大字段（TEXT/BLOB）别默认 `SELECT *` 全捞。
- 分页插件要确认有没有先 `COUNT(*)`、深分页是否可接受。

**口述短句**

> ORM 省样板代码，复杂性能路径要看真实 SQL；警惕 N+1 和事务外懒加载。

## 9. 三库开发常踩坑（速记）

| 点 | MySQL | PostgreSQL | SQL Server |
|---|---|---|---|
| 分页 | `LIMIT m,n` | `LIMIT/OFFSET` | `OFFSET/FETCH`；老写法 `TOP` |
| 字符串拼接 | `CONCAT` / `||`（看 sql_mode） | `||` | `+` |
| 自增 | `AUTO_INCREMENT` | `SERIAL` / `IDENTITY` / sequence | `IDENTITY` |
| 布尔 | 常用 `TINYINT(1)` | 真 `BOOLEAN` | `BIT` |
| upsert | `ON DUPLICATE KEY` | `ON CONFLICT` | `MERGE` |
| 大小写 | 库表名与系统大小写敏感设置有关 | 未加引号则折成小写 | 默认常不敏感（排序规则相关） |
| 返回插入 id | `LAST_INSERT_ID()` | `RETURNING id` | `OUTPUT INSERTED.id` |
| 默认隔离 | RR | RC | RC |

更多见 [`三库对比速查.md`](./三库对比速查.md)。

**口述短句**

> 换库先对一下分页、自增、upsert、字符串和隔离级别默认值，这些是业务代码最常踩的差异。

## 10. 落地检查清单（写功能自测）

- [ ] 表有主键、合理索引，字符集对  
- [ ] 写路径有事务边界，无远程调用夹在中间  
- [ ] 查询走参数绑定；动态列名有白名单  
- [ ] 列表分页策略明确（深分页有方案）  
- [ ] 批量写入有批次大小与幂等  
- [ ] 连接池与实例数乘积可控  
- [ ] 关键路径看过真实 SQL / `EXPLAIN`
