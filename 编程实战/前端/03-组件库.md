# 组件库：怎么选、怎么用

> 代表仓库 README：`../开源精选/frontend/ant-design-README.md`（MIT）  
> 生态索引：`../开源精选/frontend/awesome-react-README-节选.md`

## 对比速查

| 库 | 风格 | 定制 | 体积/方式 | 适合 |
|---|---|---|---|---|
| **Ant Design (antd)** | 中后台企业风 | Design Token / CSS-in-JS | 按需 + tree-shake | 国内中后台、CRUD 多 |
| **MUI (Material UI)** | Material Design | Theme + sx | 成品样式组件体系；headless 原语另选 | 国际化产品、要 Material |
| **shadcn/ui** | 现代极简 | **拷贝进项目**改源码 | 源码 + Tailwind；底层原语依版本/方案 | 要掌控样式、定制强 |
| Chakra / Mantine | 开发体验好 | theme | 完整体系 | 中小型产品快速出活 |

**选型口述**：中后台偏 antd；要跟设计系统深度定制偏 shadcn；要 Google Material 偏 MUI。团队已有一套就别混两套重型库。

## 接入概要

### Ant Design

```bash
pnpm add antd
```

```tsx
import { Button, ConfigProvider } from "antd";
import zhCN from "antd/locale/zh_CN";

export function App() {
  return (
    <ConfigProvider locale={zhCN}>
      <Button type="primary">提交</Button>
    </ConfigProvider>
  );
}
```

要点：用 `ConfigProvider` 统一语言/主题；表格、表单、Modal 是中后台三板斧；大数据表格注意虚拟滚动与分页。

### MUI

```bash
pnpm add @mui/material @emotion/react @emotion/styled
```

用 `ThemeProvider` + `createTheme`；布局常用 `Box` / `Stack` / 对应版本的 `Grid`。

### shadcn/ui

```bash
pnpm dlx shadcn@latest init
pnpm dlx shadcn@latest add button
```

组件代码落在你仓库（如 `components/ui`），可直接改；依赖 源码 + Tailwind；底层原语依版本/方案 无障碍原语。

## 和业务封装

1. **再包一层**：`AppButton`、`AppTable`，统一 loading、权限、空态。  
2. **别改 node_modules**：主题/CSS 变量/拷贝源码（shadcn）三选一。  
3. **按需**：只引用到的组件；注意打包分析。  
4. **表单**：antd Form / React Hook Form + zod；复杂校验放 schema。

## 和 Storybook

组件库官方常自带文档站；业务二次封装的组件应进 Storybook，保证各状态可点可看（见 `04-Storybook.md`）。

## 加厚：选型不只比“好看”和下载量

| 维度 | 需要验证的具体问题 |
|---|---|
| 业务复杂度 | 大表格、表单联动、日期/时区、树选择是否够用？ |
| 设计系统 | Token 能否覆盖颜色、间距、圆角、暗色与品牌变体？ |
| 无障碍 | 键盘路径、焦点管理、读屏标签、对比度是否经过验证？ |
| 工程兼容 | React/SSR 版本、样式注入顺序、包体、国际化是否匹配？ |
| 维护成本 | 升级频率、破坏性变更、封装范围、许可证和贡献机制如何？ |

先选一个真实的复杂页面做试点，记录实现难点、初始包体和可访问性问题，再决定。Tree shaking 需要 ESM、构建配置和包声明等配合，“按需 import”不保证所有相关样式都最小。

## 加厚：业务封装的边界

- **基础视觉层**：统一 Button、Input 等风格和默认行为，尽量保留原库有用能力。
- **业务层**：UserPicker、OrderStatusTag 等表达领域概念，依赖业务 API 时单独管理。
- 不把所有组件都塞入一个“万能表格”数百个参数；可组合的列、工具栏、筛选与分页更易测试。
- 受控组件明确 value/onChange 的单一来源；不要同时在内部复制一份 props 状态，又让外部强行覆盖。
- loading 禁用提交只是体验保护，不代替服务端幂等；前端重试、重复点击与多窗口仍可能发生。

## 常见坑

1. 弹窗在 Portal 中渲染，z-index、滚动锁和主题上下文要验证；不要用越来越大的 z-index 遮盖层级错误。
2. 表格用行号当 rowKey，翻页/重排后选中项串行；使用稳定业务 ID，并明确跨页选择策略。
3. 表单 initialValues 常仅用于初始化，接口回来后是否需 reset/setFields 要看组件 API；不要以为 props 变了必自动同步全部字段。
4. 日期选择器显示的是日期对象，接口可能需要时间点/日期字符串；明确时区、空值与格式，别直接 JSON.stringify 凑合。
5. 国际化不是换一份 locale 就结束：日期库、数字/货币、RTL 和业务文案都可能需单独设置。
6. Headless primitive 帮你提供交互/无障碍基础，但自定义样式和组合后仍需测试；“库支持 a11y”不保证你的页面合规。

## 验收清单

至少在 Storybook 记录默认、禁用、loading、错误、长文本、窄屏、暗色、键盘导航状态。升级组件库时跑这些故事的交互/视觉回归，并检查焦点回到触发按钮、表单错误能否读出等真实路径。

## 面试口述

> 我先用业务需求和设计系统选组件库，而不是只看流行度。成品库适合快速做复杂页面，headless 或源码型方案给更多控制，但也带来维护与无障碍责任。封装分基础视觉和领域业务两层，保持受控数据流与稳定行标识。再用 Storybook 把边界状态和升级回归固化下来。
