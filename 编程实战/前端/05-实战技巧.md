# 前端实战技巧

## 工程化

- 脚手架：Vite + React + TS；全栈可选 Next.js（见开源 `nextjs-README.md`）。  
- 规范：ESLint + Prettier + husky + lint-staged。  
- 路径别名：`@/` → `src/`。  
- 环境：`.env.development` / `.env.production`；`VITE_` / `NEXT_PUBLIC_` 常用于暴露浏览器可读配置；这些值不能放密钥，构建工具配置也会影响暴露范围。

## 目录习惯

```
src/
  app/ or pages/     # 路由
  components/ui/     # 纯 UI
  features/<域>/     # 业务（api、hooks、components）
  hooks/ lib/ types/
```

按**业务域**拆，比按文件类型硬拆更好维护。

## 接口层

- 集中 `apiClient`（axios / fetch 封装）：baseURL、超时、token、错误码。  
- 401 → 跳登录；业务错 → toast；网络错 → 可重试。  
- 服务端状态用 React Query：`queryKey` 规范、`invalidateQueries` 写后刷新。

## 表单与表格

- 简单：组件库 Form。  
- 复杂：React Hook Form + zod。  
- 表格：服务端分页；筛选条件进 URL query，可分享可回退。

## 权限

- 路由守卫 + 按钮级权限（指令/组件 `Can`）。  
- 权限码来自后端；前端隐藏不等于安全，接口仍要鉴权。

## 性能与体验

- 路由懒加载；首屏骨架屏。  
- 防抖搜索；大上传分片。  
- 错误边界 + 监控（Sentry 一类）。

## 发布

- 静态资源 CDN；HTML 短缓存，hashed 资源长缓存。  
- 版本号 / tag；回滚预案。  
- Preview 环境对齐生产配置。

## 和 AI 协作（干活）

- 贴：**报错全文 + 相关文件 + 期望行为**。  
- 让 AI 写 story / 单测边界，你负责对一下真实设计稿。  
- 生成的 antd/MUI 代码要过一遍：是否多余重渲染、是否无障碍。

## 加厚：以“一次编辑保存”串起工程边界

1. 路由/URL 保存资源 ID、筛选与分页，刷新和返回后能恢复上下文。
2. 查询层获取服务端实体；表单初始化为独立草稿，未保存修改不要直接写入共享查询缓存。
3. 提交前做前端校验，后端再次校验权限、版本/约束；需要时带幂等键或版本号。
4. 保存成功后，按资源和列表 queryKey 精确失效/更新缓存；关闭弹窗前明确是否等待成功。
5. 保存失败保留草稿，展示字段错误或可重试提示，不把所有错误都变成“网络异常”。

| 状态放哪里 | 示例 | 原因 |
|---|---|---|
| URL | 搜索词、页码、tab | 可分享、可回退 |
| 本地 UI state | 弹窗开关、未提交表单 | 生命周期短，避免全局污染 |
| 服务端查询缓存 | 用户详情、分页结果 | 有时效、失效和后台刷新语义 |
| 服务端权威数据 | 权限、库存、订单状态 | 浏览器不能成为安全/一致性裁判 |

## 加厚：请求层要区分失败类型

- 网络失败、超时/取消、HTTP 非 2xx、业务拒绝分别处理；用户取消不应弹“服务器崩溃”。
- 401 和 403 不一样：前者通常表示未认证/凭据失效，后者可能是已登录但无权；不要无限刷新 token。
- 多个请求同时 401 时，刷新流程应单飞并有退出条件；更新凭据要遵守实际安全方案。
- 自动重试读请求也需限制次数与退避；写请求只有幂等语义明确时才重试。
- TypeScript 类型不会在运行时校验后端响应，关键边界用 schema 检查，避免把 HTML 错页当 JSON 数据。

## 加厚：SSR、缓存与发布

SSR 首屏让服务器先输出 HTML，再由客户端水合；Client Component 不是“后端密钥可在里面用”。浏览器可拿到的环境变量与序列化 props 都应视为公开数据。Next.js 的服务端/客户端边界与缓存行为按项目版本核验，不把旧版默认缓存规则当永久规则。

发布时 HTML 引用新版本 hashed 资源，要保证资源先可用，并保留回滚所需旧资源；否则用户持有旧 HTML 却加载不到旧 chunk。Service Worker 还可能维持旧缓存，要有升级策略。数据库/API 变更先向后兼容，不能只回滚前端包就假定所有系统都回来了。

## 常见坑

- queryKey 没包含用户/租户/筛选条件，造成串数据或页面显示旧列表。
- 乐观更新没有保存旧值与失败恢复，还与后台刷新互相覆盖；复杂账务状态先采用服务端确认更稳。
- 防抖只减少发起次数，不自动解决在途请求竞态；还需取消或版本标识。
- 将 token 放在能被脚本读的地方就认为“有鉴权所以安全”；同时考虑 XSS、CSRF、Cookie 属性与接口设计。
- 认为所有 `VITE_` / `NEXT_PUBLIC_` 变量是运行时注入；很多值构建时已写入 bundle，部署后改容器变量未必生效。
- 只用前端隐藏按钮保护数据；后端必须按用户与资源逐次授权。

## 面试口述

> 我把前端工程拆成 URL 状态、交互草稿和服务端数据三层，保存流程明确校验、提交、错误保留和缓存失效。请求层区分取消、网络、HTTP 和业务错误，写重试必须先有幂等语义。SSR 与客户端边界要防止密钥和用户数据泄漏，发布要兼容旧资源与旧 API。工程化的目标是状态可解释、故障可定位、回滚可执行，而不只是工具装得多。
