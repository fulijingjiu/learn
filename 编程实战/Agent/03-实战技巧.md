# 03 · 实战技巧

## 1. 工具设计（比提示词更重要）

- **一个工具一件事**；名字像函数：`search_orders`，不要 `do_stuff`。
- 参数用 JSON Schema / Pydantic；必填少而准。
- 返回**结构化短结果**（id、状态、错误码），别甩整页 HTML。
- 失败要可区分：`not_found` / `timeout` / `permission_denied`，方便模型改策略。
- **幂等**：同一参数重复调用尽量安全（尤其写操作）。

## 2. 提示与指令

- 系统提示写清：角色、可用工具、何时停、禁止事项。
- 明确「不知道就说不知道 / 再查」，减少瞎编工具参数。
- 给 1～2 个 few-shot 工具调用示例往往比长篇理论管用。

## 3. 循环与预算

- 设 `max_iterations` / token 预算，防死循环烧钱。
- 同一工具连续失败 N 次 → 升级给人，不要死磕。

## 4. 评测 Eval（上线前）

- 固定题集：成功路径 + 边界 + 恶意指令（越权、诱导转账）。
- 看轨迹：调了哪些工具、顺序对不对，而不只看最终句子。
- 回归：改提示/模型后重跑同一套。

## 5. 安全红线（开发必做）

| 红线 | 做法 |
|---|---|
| 擅自发邮件 / 转账 / 下单 | 默认禁用；要开必须人审 |
| 密钥进提示或日志 | 环境变量；日志脱敏 |
| SQL / Shell 注入 | 参数化；命令 allowlist；禁任意 shell |
| 删改生产数据 | 只读工具为主；写操作二次确认 |
| 提示注入 | 不把不可信网页全文当系统指令 |

## 6. 和全栈的结合点

- 后端：工具 = 你的业务 API（订单、库存）。
- 前端：展示「正在调用 xxx」「等待确认」。
- 运维：密钥、限流、审计日志、容器隔离代码执行。
